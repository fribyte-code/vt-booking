# API Design

The REST API consumed by the React SPA. **Status:** proposal for review. Labels (REQ/REC/ASM) are explained in [`ARCHITECTURE.md`](ARCHITECTURE.md). The tables referenced are in [`DATABASE_DESIGN.md`](DATABASE_DESIGN.md).

---

## 1. Conventions

| Topic | Decision |
|---|---|
| Base path | `/api/v1`, on the same origin as the SPA (Nginx proxy). Versioning is cheap insurance for future integrations. We don't plan to run multiple versions side by side; the SPA and API are deployed together. |
| Not versioned | OIDC endpoints (`/oauth2/**`, `/login/oauth2/**`, owned by Spring Security) and ICS feeds (`/ical/{token}.ics`). Feed URLs are a stable external contract, because users paste them into Google Calendar. |
| Format | JSON, `camelCase`. Field names follow the prototype's `src/types/index.ts` where possible. |
| IDs | UUID strings |
| Time | Requests: ISO-8601 with offset. Responses: UTC `Z`. Business time zone `Europe/Oslo`. |
| Auth | Session cookie `__Host-SESSION`. Mutating requests need the `X-XSRF-TOKEN` header. |
| Identity | **Never** taken from the request body, query or path. The actor is always the session user (RISK-02). DTOs have no `userId`, `actorId` or `requestedById` input fields. |
| Errors | RFC 9457 Problem Details (§5) |
| Contract | The OpenAPI 3.1 document is generated by springdoc at `/api/v1/openapi.json` (dev and staging only). The SPA generates its TypeScript types from it. |
| Layering | Controller → service → repository. Controllers parse input, resolve the `Actor` and map exceptions. **All rules and authorization run in services** (`ARCHITECTURE.md` §3). |

### Pagination, filtering and sorting

- **Lists:** `?page=0&size=25` (max `size=100`). Response:

  ```json
  { "items": [ ... ], "page": 0, "size": 25, "totalItems": 312, "totalPages": 13 }
  ```

  Offset pagination is fine at this data size.
- **The audit log** uses keyset pagination (`?before=<id>`), because it grows without bound.
- **Filters** are explicit query parameters per endpoint, such as `status`, `roomId`, `organizationId`, `from`, `to` and `q` (case-insensitive search on name/title). No generic filter language.
- **Sort:** `?sort=start` or `?sort=-decidedAt`, from a whitelist per endpoint.

### Date-range queries (calendar)

- `from` and `to` are **required** and half-open `[from, to)`. They match FullCalendar's `datesSet` `currentStart`/`currentEnd` (or `activeStart`/`activeEnd`).
- The maximum span is **62 days**. Month view needs about 42. Larger spans get `400 VALIDATION`.
- The calendar is not paginated. The range cap bounds the size.
- Overlap semantics: an event is included if `period && [from, to)`. It uses the GiST index.

## 2. Endpoints

**Legend for "Who":**

| Code | Meaning |
|---|---|
| **A** | any authenticated user |
| **M(org)** | current member of that organization |

### 2.3 Calendar

| Method | Path | Who | Purpose |
|---|---|---|---|
| GET | `/api/v1/calendar/events?from&to&roomIds=a,b&includePending=true` | A | Events for the calendar view (minimal projection) |
| GET | `/api/v1/rooms/{id}/busy?from&to` | A | Busy intervals only. For the booking form's "is it free" hint. |

**Event projection.** Fields are filtered per viewer; RISK-03.

```json
{
  "id": "0194…", "roomId": "0191…", "kind": "BOOKING",
  "start": "2026-10-14T14:00:00Z", "end": "2026-10-14T16:00:00Z",
  "status": "APPROVED",
  "title": "Styremøte",
  "organization": { "id": "0193…", "name": "Organisasjon A" },
  "seriesId": null,
  "isOwnOrganization": true,
  "canEdit": true,
  "version": 3
}
```

Visibility rules:

- `APPROVED` bookings and blocks: visible to all authenticated users, with title and org name (ASM, Q-05).
- `PENDING`: included only for members of the booking's org and for admins. Others don't see pending requests (Q-06). This changes the prototype, which showed every pending request to everyone.
- Never included in this projection: `description`, the requester's identity, decision fields.
- `canEdit` is computed by the server from the same rules as `PATCH`. It drives FullCalendar's per-event `editable`.

### 2.4 Bookings

| Method | Path | Who | Purpose |
|---|---|---|---|
| POST | `/api/v1/bookings/preview` | M(org) | Dry run: the same validation as create, but nothing is persisted. Debounced live feedback in the form. |
| POST | `/api/v1/bookings` | M(org), effective permission ≠ NONE | Create. Returns `201` with status `APPROVED` (DIRECT) or `PENDING` (REQUEST). |
| GET | `/api/v1/bookings/{id}` | A (fields filtered); full details for M(org) and ADM | Details dialog |
| PATCH | `/api/v1/bookings/{id}` | see rules below | Reschedule (drag/resize) and/or edit text. Body includes `version`. |
| POST | `/api/v1/bookings/{id}/cancel` | owner, OA(org), ADM | `{ reason?, version }` |
| POST | `/api/v1/bookings/{id}/approve` | ADM | `{ version, comment? }`. Re-validates (`DATABASE_DESIGN.md` §5). |
| POST | `/api/v1/bookings/{id}/reject` | ADM | `{ version, reason }`. The reason is required (max 300 characters). |

**Create request:**

```json
{
  "roomId": "0191…",
  "organizationId": "0193…",
  "title": "Seminar",
  "description": "Formål, forventet antall, utstyr …",
  "expectedAttendees": 40,
  "start": "2026-10-21T12:00:00+02:00",
  "end": "2026-10-21T14:00:00+02:00"
}
```

**Preview response** (also the shape of `RULE_VIOLATION` details):

```json
{
  "permission": "REQUEST",
  "outcome": "WILL_BE_PENDING",
  "violations": [],
  "conflicts": [
    { "start": "…", "end": "…", "title": "Quizkveld", "organizationName": "Organisasjon C" }
  ]
}
```

- `outcome` is one of `WILL_BE_APPROVED`, `WILL_BE_PENDING` or `NOT_ALLOWED`.
- `conflicts` respects visibility: other organizations' *pending* requests are never listed.

**Who may reschedule (PATCH `start`/`end`/`roomId`).** Provisional rules, Q-15:

| Booking state | Actor | Allowed? | Result |
|---|---|---|---|
| `APPROVED`, org has **DIRECT** on the target room | owner or OA(org) | yes, if all rules pass | stays `APPROVED` |
| `APPROVED`, org has **REQUEST** on the target room | owner or OA(org) | **no**: `409 INVALID_STATE` ("Kontakt administrator eller send ny søknad") | — |
| `PENDING` | owner | yes, if rules pass | stays `PENDING`, keeps its place in the queue |
| any active booking | ADM | yes (limits bypassed, conflicts not) | unchanged status, audited |
| `REJECTED`, `CANCELLED`, or already started | anyone | no | `409 INVALID_STATE` |

Editing title or description is allowed for owner and OA(org) on `PENDING` and future `APPROVED` bookings.

**Admin booking management:**

| Method | Path | Who | Purpose |
|---|---|---|---|
| GET | `/api/v1/admin/bookings?status&roomId&organizationId&from&to&q&page&sort` | ADM | Pending queue, history ("Behandlet"), and all bookings |
| GET | `/api/v1/admin/bookings/{id}/competing` | ADM | Overlapping pending requests and approved conflicts. The data behind today's warnings in `AdminPage.tsx`. |
| POST | `/api/v1/admin/bookings/bulk-approve` | ADM | `{ items: [{ id, version }] }`. Per-item results; never all-or-nothing. |
| POST | `/api/v1/admin/bookings` | ADM | Create on behalf of an org (`organizationId` required) or a block (`kind: "BLOCK"`, `reason`). Limits bypassed, audited. |

| GET | `/api/v1/invitations/{token}` | A | Shows the org name and role for a confirmation page |
| POST | `/api/v1/invitations/{token}/accept` | A | Creates the membership. Single use; returns 410 if expired. |
| GET | `/api/v1/organizations/{id}/room-access` | M(org), ADM | Effective permission per room for this org |
| GET | `/api/v1/organizations/{id}/bookings?from&to&status&page` | M(org), ADM | The org's bookings |

**Escalation guards:**

- OA(org) can only grant `MEMBER` or `ORG_ADMIN` **in its own org**.
- OA(org) cannot change `globalRole`, room access or quotas.
- Role changes are audited.


### 2.9 Calendar feeds (ICS)

| Method | Path | Who | Purpose |
|---|---|---|---|
| GET | `/ical/{token}.ics` | holder of a valid, unrevoked token | `text/calendar`. Contents are computed with the feed owner's current permissions (`ARCHITECTURE.md` §8). |

**Rules for this endpoint:**

- Unknown, revoked and owner-disabled tokens all return `404`. They are indistinguishable.
- Rate limit: 30 requests per minute per IP, enforced in Nginx.
- No cookies are used or set, and there is no CSRF exposure, because it is GET-only.
- The token is excluded from access logs. Nginx logs `/ical/<redacted>`.

## 3. Authorization matrix (test oracle)

This is the source of truth for the automated authorization matrix tests (C-18). The setup is:

- User **U1**: MEMBER of org A
- User **U2**: ORG_ADMIN of org A
- User **U3**: MEMBER of org B
- User **U4**: no membership
- **ADM**
- Booking **bA**: org A, created by U1
- Room **R**: A = DIRECT, B = REQUEST

| Action | U1 | U2 | U3 | U4 | ADM |
|---|---|---|---|---|---|
| GET calendar events (approved) | 200 | 200 | 200 | 200 | 200 |
| See bA in calendar while PENDING | ✓ | ✓ | ✗ (absent) | ✗ | ✓ |
| GET `/bookings/bA` description | ✓ | ✓ | ✗ (field omitted) | ✗ | ✓ |
| POST booking for org A in R | 201 APPROVED | 201 | 403 NOT_MEMBER | 403 NOT_MEMBER | 403 (not a member; use the admin endpoint) |
| POST booking for org B in R | 403 | 403 | 201 PENDING | 403 | 403 |
| PATCH bA (reschedule) | 200 | 200 | 403* | 403* | 200 |
| Cancel bA | 200 | 200 | 403* | 403* | 200 |
| Cancel bA after U1 is removed from A | 403 for U1 (VULN-07) | 200 | 403* | 403* | 200 |
| Approve or reject any request | 403 | 403 | 403 | 403 | 200 |
| Approve after the org's permission → NONE | — | — | — | — | 409 / 403 NO_PERMISSION (VULN-04) |
| Manage members of A | 403 | 200 | 403 | 403 | 200 |
| Make self ORG_ADMIN of B | 403 | 403 | 403 | 403 | 200 |
| Change room access | 403 | 403 | 403 | 403 | 200 |
| GET `/admin/users` | 403 | 403 | 403 | 403 | 200 |
| Body contains `"requestedById": "<ADM id>"` | ignored | ignored | ignored | ignored | ignored |
| Unauthenticated, any `/api/v1/**` except providers, csrf and health | 401 | | | | |

\* 403 while bA is `APPROVED`, because approved bookings are visible to everyone. 404 while it is `PENDING`, because it is invisible to them.

**On 404 vs 403:**

- *Objects* the actor cannot see return 404.
- *Actions* on visible objects that the actor lacks rights for return 403.
- *Collections or roles*, such as admin endpoints, return 403.

## 4. Validation

- **Bean Validation on every request DTO**, applied on top of the DB constraints:
  - `@NotBlank @Size(max = 80)` title
  - `@Size(max = 500)` description
  - `@Size(max = 300)` reason and comment
  - `@Positive` attendees
- **Unknown JSON fields are rejected** (`FAIL_ON_UNKNOWN_PROPERTIES = true`). It's a clearer failure than silently ignoring them. Identity fields are absent from DTOs anyway.
- **Strings** are trimmed. Control characters other than `\n` and `\t` are stripped.
- **Times:** must parse with an offset, and `end > start`. The finer business rules live in `BookingRules`.
- **Body limit:** 64 KB (Nginx `client_max_body_size` and Spring).
- **Every list endpoint has a maximum page size.** Every range endpoint has a maximum span.

## 5. Error handling

All errors use `application/problem+json` (Spring's `ProblemDetail`):

```json
{
  "type": "https://<host>/problems/conflict",
  "title": "Conflict",
  "status": 409,
  "code": "CONFLICT",
  "detail": "Møterom A er allerede booket i dette tidsrommet.",
  "requestId": "01J…",
  "conflicts": [ { "start": "…", "end": "…", "title": "Styremøte", "organizationName": "Organisasjon A" } ]
}
```

| `code` | HTTP | When | Prototype equivalent |
|---|---|---|---|
| `VALIDATION` | 400 | Malformed input; `errors: [{ field, message }]` | `VALIDATION` |
| `UNAUTHENTICATED` | 401 | No or expired session | — |
| `FORBIDDEN` | 403 | Role missing | `FORBIDDEN` |
| `NOT_MEMBER` | 403 | Booking for an org you are not in | `NOT_MEMBER` |
| `NO_PERMISSION` | 403 | Effective permission is NONE | `NO_PERMISSION` |
| `NOT_FOUND` | 404 | Missing or invisible | `NOT_FOUND` |
| `CONFLICT` | 409 | Overlap with an approved booking or block (incl. DB `23P01`) | `CONFLICT` |
| `INVALID_STATE` | 409 | Wrong status for the transition, or the booking has already started | `INVALID_STATE` |
| `VERSION_CONFLICT` | 409 | Stale `version` | — |
| `GONE` | 410 | Expired invitation | — |
| `RULE_VIOLATION` | 422 | Limits, opening hours, quotas; `violations: [{ code, detail }]`, e.g. `MAX_DURATION`, `OUTSIDE_OPENING_HOURS`, `PENDING_QUOTA` | (VULN-03/05 rules) |
| `RATE_LIMITED` | 429 | Rate limit hit | — |
| `INTERNAL` | 500 | Anything else. Generic `detail` and a `requestId`. No stack trace (C-13). | `errorMessage()` fallback |

- **`detail` messages are Norwegian** and safe to show directly. The SPA shows them as today in `lib/errors.ts`, keyed on `code` for special handling. The app is Norwegian-only (Q-25), so the server owns the message text, and the rule messages stay next to the rules.
- **Codes are stable** and part of the API contract.
